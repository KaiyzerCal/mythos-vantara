[2026-08-22] INCIDENT → app auth outage during migration apply. A CREATE TABLE for two new empty tables carried REFERENCES auth.users(id); the FK needed a lock on auth.users, the statement queued rather than acquiring, and because Postgres queues lock requests in order every sign-in blocked behind it. The auth service stalled (requests timing out at origin) and the connection pool exhausted. No SQL path was reachable for recovery — the Lovable SQL editor returned "Connection terminated due to connection timeout" and query_database returned 499 on every call including `select 1` — so recovery required Lovable restarting the backend. Nothing was lost: the transaction never committed and the tables were new with nothing referencing them. Diagnostic note for next time: control plane healthy (get_me, get_database_status both fine) while every query times out means the database is blocked, not absent; and reads failing does NOT rule out a lock, because a lock can exhaust the pool — that inference was made during this incident and was wrong. Prevention landed in code, not just advice: both migrations now SET lock_timeout='3s' / statement_timeout='60s' at the top so a DDL statement fails fast instead of becoming a head-of-line block, and CLAUDE.md gained a "Database Changes — Read Before Any DDL" section (lock_timeout mandatory; treat auth.users as radioactive and prefer user_id + RLS over an FK; every migration must be re-runnable so a lock timeout can't leave a half-applied schema; a cancelled DDL is an unknown, not a failure — verify schema state before retrying).
